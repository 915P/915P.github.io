**全量编译 56 秒**，装编译依赖 9 分 42 秒，匿名化重建 99 秒。我事前问 LLM「大概要多久」，它答「约 10 分钟」。

## 三个都不满意，于是决定自己编

这台机器是 Ubuntu 24.04（Linux Mint 22.3），Intel Arrow Lake-P 核显。想用最新的 VLC 3.0.24，发现三条路全堵：

| 方案 | 问题 |
|---|---|
| apt 官版 | 停在 `3.0.20`（`3.0.20-3build6`），而 VideoLAN 已经发到 `3.0.24` |
| snap 版 | 装上试过，硬件加速开不起来 |
| 网上的预编译包 | 来源不明的第三方 deb，不敢装 |

于是走源码编译。`build-dep`、configure 报错、链接失败这些环节我不想手动过一遍，整个过程交给 LLM 编码代理（OpenCode）执行，我负责定验收标准：硬解要有解码日志、下载文件要对得上官方校验和、装完系统里只能有一个 VLC。

## 源码下载：USTC 有 VideoLAN 镜像

所有能走 USTC 的都走 USTC（IPv6 教育网出口，快）：

```console
$ curl -o vlc-3.0.24.tar.xz https://ipv6.mirrors.ustc.edu.cn/videolan-ftp/vlc/3.0.24/vlc-3.0.24.tar.xz
27620304 bytes in 8.9s   (3.1 MB/s)
$ sha256sum vlc-3.0.24.tar.xz
e7cab503d1d7d5849b89d2cf0e1ee60d0ef6d012407791b644b9cfc0cc225fdf   ← 与 VideoLAN 官网公布值一致
```

直接 curl 会吃 403：USTC 拦了默认 User-Agent，换 UA 后又弹一个 JS 验证页，页面要求写进 cookie 的内容是本机 IPv6 地址（`addr=<IP>`），带上就过了。apt 那边没有波折，USTC IPv6 拉 62.4 MB 元数据用了 14 秒。

## 环境：编译放进 Docker，系统一行不碰

方案是容器化：拉一个 `ubuntu:24.04`，把 Ubuntu 官方 vlc 包的全套编译依赖（`apt-get build-dep vlc`，约 300 个包）装进去，源码目录挂载进来编译。编译阶段因此完全不需要 root，产物落在宿主机目录里，装不装、什么时候装由我决定。

第一个来回花在这里：`ubuntu:24.04` 基础镜像没有 `ca-certificates`，apt 走 HTTPS 到 USTC 时证书校验失败，`apt-get update` 却只报 warning 不返回错误，所有包都变成 `Unable to locate package`。把宿主机的 CA bundle 复制进镜像才解决。

VA-API 这边，机器上已有 Intel 的 kobuk PPA（libva 2.24 + iHD 驱动 26.3.5，Arrow Lake 要靠它），这个源 USTC 没有镜像，保留原样。驱动版本决定硬解能不能跑，先用 `vainfo` 验一遍：

```console
$ vainfo
libva info: Trying to open /usr/lib/x86_64-linux-gnu/dri/iHD_drv_video.so
vainfo: Driver version: Intel iHD driver for Intel(R) Gen Graphics - 26.3.5 ()
      VAProfileH264Main  : VAEntrypointVLD      ← 共 24 个解码入口
```

## 编译与打包：实测时长

configure 打开硬件加速开关：

```bash
./configure --prefix=/usr/local --enable-libva --enable-vdpau
# checking for LIBVA... yes    checking for LIBVA_DRM... yes
# checking for LIBVA_X11... yes    checking for VDPAU... yes
```

各阶段实测（14 核，文件时间戳测量）：

| 阶段 | 耗时 | 备注 |
|---|---|---|
| 下载源码 27.6 MB | 8.9 s | USTC IPv6 |
| 构建 Docker 镜像（装 ~300 个依赖） | 9 分 42 秒 | 一次性，之后全程复用 |
| `configure` | 14 s | |
| `make -j14` 全量编译 380 个插件 | 56 秒 | |
| `make install` → staging | 33 s | |
| 匿名化重建全流程 | 99 秒 | configure + make + install |

LLM 的预估「约 10 分钟」按重建一次算，实测 99 秒。它把一次性成本和边际成本混在了一起：常驻开销是那个 9 分 42 秒的镜像，编译本体不到一分钟。

打包成 deb 有两个设计，让它像系统包一样干净：

1. `Depends` 用扫描结果算：对 staging 里的全部共享库与可执行文件（392 个）跑 `ldd`，把每个实际链接的库映射回 dpkg 包名，得到 236 项依赖；
2. `Conflicts`/`Replaces` 列全官版 16 个包（`vlc`、`vlc-bin`、`libvlc5`、全部 `vlc-plugin-*`……），于是 `sudo apt install ./vlc_3.0.24-1_amd64.deb` 一条命令就是替换，apt 记录保持一致，之后 `apt remove vlc` 照常能管。

依赖链里出岔子的是 Ubuntu 的 `phonon4qt5`：它硬依赖 `phonon4qt5-backend-vlc | phonon4qt5-backend`，后者又依赖被我们移掉的 `vlc-plugin-base`，连锁反应会把 okular 一起卸掉。解法是同一句 apt 命令里补一个替代后端：

```bash
sudo apt install ./vlc_3.0.24-1_amd64.deb phonon4qt5-backend-gstreamer
```

模拟安装（`apt -s`）确认 okular 不受影响后才动手，apt 版 16 个包卸得没有残留。

## 硬件加速验证：解码日志，以及一次误判

验收标准定在解码日志上。跑一段 H.264，`-vvv` 抓到完整证据链：

```console
avcodec decoder debug: available hardware decoder output format 44 (vaapi)
main generic debug: using hw decoder module "vaapi_drm"
[AVHWDeviceContext] VAAPI driver: Intel iHD driver for Intel(R) Gen Graphics - 26.3.5 ().
avcodec decoder: Using Intel iHD driver for Intel(R) Gen Graphics - 26.3.5 () for hardware decoding
```

对照组（`--avcodec-hw=none`）这行出现 0 次，它确实来自硬件路径。

问题出在测试方法上：我先用 `--vout dummy` 做无头测试，默认参数下得到 `no hw decoder modules matched`，一度以为硬解没编进去。VLC 的 VAAPI 有 X11 / DRM 两条后端，X11 后端要求 vout 提供 VA 表面（dummy vout 给不了），默认的 `any` 只选 score > 0 的模块。换成真实 GUI 窗口播放，默认设置一切正常。

## 发布前的收尾：匿名化与 GPL

准备发到 GitHub 时发现 `vlc --version` 的输出里嵌着编译机的主机名和我的用户名（configure 阶段 `hostname -f` / `whoami` 烧进去的）。查了下 `configure.ac`，两个值都支持环境变量覆盖，不用改任何源码：

```bash
VLC_COMPILE_HOST=build-host VLC_COMPILE_BY=builder ./configure ...
```

重建一次 99 秒，全树 `grep` 确认无残留，发布版显示 `Compiled by builder on build-host`。

GPL 要求二进制能对应到源码，Release 里附上了那份 sha256 与官方一致的原始 tarball（文件本身未改动；v3 起构建时会另打 4 行补丁，见后文），README 写明 configure 参数与 unofficial 免责声明（VLC 是 VideoLAN 的商标）。

## 更新（11 月 2 日）：一份审核报告与 v3.0.24-2

发布次日，另一份 LLM 审核报告指出打包层的两个问题，复核后两条都成立，当天发出 v3.0.24-2：

- 缺 `Provides`（最重的一条）：任何 `Depends: libvlc5` 的第三方包装上来，`apt -s` 显示的计划是 `Remv vlc`，静默卸掉我们自己、再装回 Ubuntu 3.0.20 的库。我用一个最小探针包复现，补上版本化 `Provides` 后，同一模拟保留本包、依赖方照常满足，连 `phonon4qt5-backend-vlc` 都能直接装回。之前用 gstreamer 后端绕依赖链，绕开的只是症状。
- `Conflicts` 漏了 5 个：noble 源里还有 jack/pipewire/bittorrent/fluidsynth/svg 五个插件包没列，`apt install vlc-plugin-jack` 会触发和上面一样的拆除；补全后 apt 干净报错、本包保留。
- 顺带补了两个规范项：`Installed-Size`，以及显式 `libc6 (>= 2.38)`（实测 payload 最高符号版本就是 `GLIBC_2.38`）。

报告里也有不成立的：比如"主二进制可能是 libtool wrapper 导致依赖漏扫"，`file` 确认本构建的 `bin/vlc` 是真 ELF，启动器 cvlc/nvlc 等本就是无动态依赖的 shell 脚本。我给报告里每条结论都跑了实验，也回头补了自己当初的盲区：模拟只测了预设场景（替换官版 + 保 okular），没拿"随便一个依赖 libvlc5 的包"去砸安装方案，打包元数据就成了没验过的角落。

## 再更新（11 月 2 日）：HDR 颜色不对，根因有四层

v2 发完，播一段 HDR 片子发现颜色不对。问了份 LLM，答复指向：VLC 3.x 的 HDR→SDR 色调映射依赖 libplacebo，发行版打包时把它关了，"需要一个启用了 libplacebo 支持的构建"。这话方向对；真要落地，下面还压着三层：

- 装不上：configure 的条件写死 `libplacebo >= 0.2.1 libplacebo < 6`，Ubuntu 24.04 仓库里只有 6.338.2，`apt install libplacebo-dev` 装上来也过不了版本检查。这正是所有发行版的 VLC 都不带该功能的原因。只能本地编 libplacebo 5.264.1；tarball 不含 git 子模块（glad 缺失），meson 里把 `opengl`/`vulkan` 后端关掉即可，VLC 用的只是它的着色器层。
- 编不过：打开 `--enable-libplacebo` 后 `make` 当场失败，四个 GL 转换插件（`glconv_vaapi_wl/x11/drm`、`glconv_vdpau`）的 `_CFLAGS` 漏了 `$(OPENGL_COMMONCLFAGS)`，`converter.h` 里的 `#include <libplacebo/config.h>` 找不到头。上游把这个变量拼成了 `CLFAGS`，加上从没人开过这个开关，问题一直没暴露。补了 4 行 patch，打在生成好的 `modules/Makefile.in` 上：系统 automake 1.16.5 和 tarball 版本对不上，重新生成走不通。补丁随 Release 分发。
- 开了没反应：`vlc -H` 里 `--tone-mapping` 等选项确实出现了，日志也有 `Initialized libplacebo v5.264.1 (API v264)`，可画面纹丝不动。`target-prim`/`target-trc` 默认值是 Unknown，整条色彩管线就是恒等变换，PQ 照旧原样送显。得告诉 VLC 显示器是什么：`--target-prim=3 --target-trc=2`（BT.709/sRGB）。
- 对照实验拍错了窗口：前两轮 A/B 截图都是"0 个不同像素"，一查发现 `wmctrl -l | grep -i vlc` 匹配到的是我开着的一个浏览器窗口（它的标题里也带 VLC 字样），截图拍的一直是它，颜色当然一致。`pkill -f` 也因为模式匹配到自己，把 shell 杀了两回。改成把 VLC 窗口挪到固定位置、截全屏再裁剪：595,200 个采样像素变了 497,634 个，亮度均值 0.150 → 0.537。

另外，两个 VLC 实例同时跑，4K HEVC 会 `get_buffer() failed`（VA 表面分配失败），单实例播放 0 次报错。这次也是测试方法造成的假象，和上节 dummy vout 那次同类。

v3.0.24-3 把前三层修进包里：本地编的 libplacebo 5.264.1 参与链接、`libplacebo.so.264` 随包捆绑（LGPL，源码指针写在 README）、4 行上游补丁入库。装上后记得设 `target-prim`/`target-trc`，不然颜色照旧。

Release：<https://github.com/915P/vlc-3.0.24-ubuntu2404/releases/tag/v3.0.24-3>

## 小结

让 LLM 编译，前提一直是我这边握住验收标准：校验和对官方、硬解有日志、模拟安装确认无副作用、发布物扫过隐私。估时上它这次高估了：预估约 10 分钟，重建实测 99 秒，全量编译 56 秒。
